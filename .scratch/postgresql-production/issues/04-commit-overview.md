# 04 — 确认入库与大盘总览闭环

**What to build:** 管理员确认待确认批次后看到正在提交，最终获得确定的成功或失败结果；大盘总览读取 PostgreSQL 持久化汇总，重复请求不会重复累计。

**Blocked by:** 03 — 上传排队、解析与结果查看

**Status:** complete

- [x] 确认操作检查用户权限、归属、状态及有效期；持久化登记成功后进入正在提交，允许离开页面并重新查询。
- [x] 对同一上传批次建立幂等约束；重复点击、网络超时后的重试和工作任务重复执行只产生一次正式数据及汇总贡献。不同独立上传仍各自累计。
- [x] 正式试剂、检测结果、批次状态和汇总贡献在同一事务中原子生效；失败或进程中断不产生部分正式入库，使用批量写入而非逐行提交事务。
- [x] 总览按上传批次内有效试剂去重计数，任一有效病原体阳性即为阳性试剂；零分母显示无数据，不将结果行数或病原体计数总和当作试剂数。
- [x] 汇总贡献保留报告日期、完整地区粒度、演示标识和总体／单病原体分子分母，为后续维度查询及作废提供同一事实来源。
- [x] 总览常规请求从数据库汇总读取，不将匹配的全量明细加载到 Node 分组；索引与查询有界，明确数据版本或更新标识。
- [x] 在小数据功能场景中验证确认成功后大盘自动取得新结果，后台处理、缓存及页面刷新共同满足 30 秒预算；不能外推高负载达标。
- [x] 页面不将请求已受理误显示为提交成功；确认请求超时后查同批次状态，不自动重新上传。
- [x] 真实 HTTP 与浏览器覆盖待确认不计入、确认后计入、失败重试、少量竞争请求和重复独立上传；这类幂等正确性检查不算性能压测。
- [x] 3 人同时确认最大文件、含排队最多 1 分钟仅保留为设计目标，本阶段不验证吞吐上限。
